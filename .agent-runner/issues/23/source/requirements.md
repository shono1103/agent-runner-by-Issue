## 要件定義

### 背景

`type:feature` issue (#23) で「issueのタイトルと本文を元に定義書を作成するボタンが欲しい。結局自分でドキュメント構築まではしない。しかしドキュメントを読んで問題の有無を考えることはある。EaC作成は全て作成以外なくていい」という要望があった。現状のフローは、人間が「フォーマット作成」ボタンで空の3コメント (要件定義/システムアーキテクチャ定義/テスト定義) を作り、その本文を手で書き、その後 `convert` ジョブでAllium/LikeC4/Superpowersに変換する、という2段階になっている。issueのタイトル・本文を書いた時点で人間の言語化はほぼ終わっているのに、その内容をsourceコメント3種として整形し直す作業を再度人間がやらされている、というのが本issueの指摘である。

### 要件

1. issueのタイトル・本文のみを入力として、claude cliに「要件定義/システムアーキテクチャ定義/テスト定義」の3つのsourceコメントを自動でドラフトさせ、issueに投稿する新しいジョブ種別 `draft` を追加すること
2. `draft` ジョブの入力方向は「issue本文 → source」であり、既存の `convert` ジョブ (source3コメント → Allium/LikeC4/Superpowers、すなわち「source → EaC」) とは入力の向きが逆であること。両者は独立したジョブであり、`draft` の出力 (source3コメント) がそのまま `convert` の入力になる一直線のパイプラインを構成すること
3. `draft` ジョブが生成したsourceコメントに対して、投稿前に人間が確認・承認するステップは設けない (必須にしない)。生成されたコメントは、通常のGitHubコメント編集と同じ手段 (Web UI上での直接編集) で人間が後から自由に修正できることを前提とする。「自分でドキュメントを構築まではしない。しかしドキュメントを読んで問題の有無を考えることはある」という要望どおり、レビューは強制フローではなく生成後の任意編集として扱う
4. userscript側のUIには、`draft` ジョブに対する個別フォーマット選択 (「要件定義のみ作成」「アーキテクチャ定義のみ作成」等) は設けない。「EaC作成は全て作成以外なくていい」という要望を踏まえ、既存の「すべて生成」ボタン (convertジョブ、Allium/LikeC4/Superpowers3形式一括変換) の隣に、「定義書作成」ボタンを1つ追加するだけとする
5. `draft` ジョブを同一issueに対して再実行してもコメントが増殖しないこと。既に (人間の編集によるものか過去の生成によるものかを問わず) sourceコメントが存在するkindは上書きせず、まだ存在しないkindのみを補って生成すること

### 非機能要件

- 既存の `convert` / `create-pr` ジョブの挙動・APIには影響を与えないこと
- `draft` ジョブの実行中は対象issueに対する他ジョブの同時実行をブロックすること (既存の `convert` ジョブと同水準のissue単位ロックで足りる。git pushを伴わないためリポジトリ単位ロックは不要)
- `draft` ジョブは対象リポジトリのコードを読み取らない (issueのタイトル・本文のみを入力とする。コードを読ませる調査系ジョブとは異なる)

### Open Questions

- `draft` ジョブの入力に、issueに付与されたラベル (`type:bug` / `type:feature` / `type:task` 等) による出力内容の出し分けを行うかどうか。たとえばバグ報告issueであれば要件定義で「再現手順」を重視し、機能要望issueであれば「実現したいこと」を重視する、といった調整が考えられるが、本issueの対応範囲に含めるかは未確定
